# mitori (看取り)

**https://turntuptechnologies-ai.github.io/mitori/**

手放そうとしているドメインに、まだ何が繋がっているかを調べるツール。

ドメインは捨てた瞬間から危険になる。第三者が取得すれば、旧アドレス宛のメールでアカウントを復旧され、
残った参照はそのまま信頼を引き継ぐ。mitori は「畳み残し」を DNS 側から観測して並べる。

**バックエンドを持たない。** 検査はすべてブラウザの中で完結する。mitori 側にサーバが無いので、
誰がどのドメインを調べたかを mitori が記録・集約することは原理的にできない。
GitHub Pages のような静的ホスティングにそのまま置ける。

ただしブラウザから公開 API を直接叩く以上、照会先にはドメイン名が渡る。
現在の照会先は **DoH リゾルバ / certspotter / RDAP サーバ / archive.org / Wikimedia** の 5 系統。
外部送信の有無が稟議で問われる用途を想定しているので、隠さずここに並べておく。

## 何を見ているか

| 検査 | 使うもの | 見つかるもの |
| --- | --- | --- |
| メール受信 | MX | 手放した先の第三者が受信できる状態か（RFC 7505 の null MX は正常として扱う） |
| **SaaS 所有権トークン** | TXT | Google / Microsoft / Slack / Stripe など、まだ紐付いたままのサービス |
| グループウェア連携 | CNAME, SRV | Exchange 自動検出、Teams フェデレーションの残骸 |
| Web の生存 | A, AAAA, CNAME | コンテンツの縮退が済んでいるか |
| サブドメイン | CT ログ + DNS | 忘れられて生き残っているホスト |
| **dangling CNAME** | CNAME + 向き先の解決 | 向き先が消えた CNAME、乗っ取られやすいサービスを指す CNAME |
| **ゾーンの列挙可能性** | NSEC (DO ビット) | 歩けるゾーンなら全名前を列挙。CT ログにも辞書にも出ない名前が取れる |
| 有効な証明書 | CT ログ | 失効させずに手放そうとしていないか |
| 証明書発行の封鎖 | CAA | 新所有者が即座に証明書を取れる状態か |
| なりすまし防止 | DMARC | 冷却期間中に名前を騙られないか |
| その他 | SPF, DKIM, ACME, NS, DS, ワイルドカード | 送信系・委譲・自動更新の残骸 |
| 登録情報 | RDAP | 有効期限、レジストラ、ステータス |
| 消せない参照 | Wayback Machine | アーカイブの実在 |
| **百科事典からの参照** | Wikimedia (exturlusage) | 手放した後、新しい所有者が引き継いでしまう出典 |

とくに **TXT の所有権確認トークン**は、置いたまま忘れられやすいのに、
残っているとそのサービス側でドメインがまだ有効な資産として登録されている可能性を示す。
mitori が最も重視する検査。

**百科事典からの参照**は、消せない参照のうち唯一「手を打てる」もの。出典の URL は
ドメインを手放しても書き換わらないため、新しい所有者が記事の信頼をそのまま引き継ぐ。
失効したドメインを買って出典元を差し替える手口は実在する。
アーカイブ版への差し替えを、手放す前に済ませておく必要がある。

## 何を見ていないか

自動判定は DNS から観測できる範囲に限られる。以下は**原理的に検出できない**ので、
アプリ内では手動チェックリストとして別に並べている。

- どのサービスにこのドメインのメールアドレスを登録したか
- 被リンク全般。網羅的な索引は無料では手に入らない（商用 API は鍵と課金が要り、
  検索エンジンの `link:` は廃止済み、Common Crawl の webgraph は数十 GB あって
  ブラウザからは部分取得もできない）。権威を引き継ぐ参照だけを名指しする方針で、
  Wikimedia からの参照のみ自動判定している
- `robots.txt` / `noindex`（ブラウザから他ドメインを読むと CORS で弾かれる）
- 印刷物・看板・QR コード・名刺
- 契約書や公的届出に書かれた連絡先

**進捗 100% は「観測できる痕跡が無い」であって「手放してよい」ではない。**

## 観測結果をチェックリストに流し込む

チェックリストは「Workspace / Microsoft 365 / Slack などのドメイン所有権を解除した」のような
一般論でしか書けない。一方で検査のほうは、実際にどのサービスが紐付いているかを知っている。
知っている側から具体名を流し込むことで、汎用の心得をそのドメインの作業に変える。

```
Workspace / Microsoft 365 / Slack などのドメイン所有権を解除した
  └ Microsoft 365 / Entra ID 側でこのドメインの登録を解除する
  └ Exchange Online の自動検出（autodiscover.example.jp）をテナント側から解除する
```

各検査が `tasks` として、流し込み先の項目 id と具体的な作業を返す
（`src/lib/scan.ts` の `makeTask`）。流し込み先は `ManualItemId` 型で縛ってあるので、
存在しない項目を指す書き間違いはコンパイルで落ちる。
生成されたタスクは個別にチェックでき、状態はドメインごとに localStorage に残り、
Markdown の記録にも入れ子で出力される。

タスクの id は観測対象（サービス名・ホスト名）から作るので、件数のような
変動する値が文言に入っていてもチェック済みの状態は失われない。
逆に、対処して観測されなくなればタスクごと消える。

## 制約

- `.jp` は IANA の RDAP ブートストラップに登録がなく、JPRS は WHOIS しか提供していない。
  有効期限はブラウザからは取得できないため「判定不能」として扱う。
- CT ログは certspotter を使う。crt.sh は CORS ヘッダを返さないため採用していない。
  未認証だとレート制限があるうえ、**有効期限内の証明書しか返さない**。
  忘れられたホストほど証明書が失効しているため、CT ログによる列挙は網羅ではない。
  この但し書きは結果画面にも必ず出している。
- dangling CNAME の判定で NXDOMAIN は当てにならない。存在しない名前に NOERROR を返すゾーンが
  珍しくないため、rcode ではなく「向き先がアドレスを持つか」を主軸にしている。
  逆に S3 / Netlify / GitHub Pages などはリソースが解放されていてもワイルドカードで解決するため、
  DNS だけでは確定できない。これらは「要確認」として区別して報告する。
- サブドメインの生存確認は DoH のクエリ数を抑えるため上限を設けている。
  打ち切った場合は件数を結果に明示する。
- NSEC ウォークが効くのは、DNSSEC で署名され、かつ NSEC を素直に返すゾーンだけ。
  NSEC3（ハッシュ化）とホワイトライ（RFC 4470、聞かれた名前のすぐ隣までしか無い NSEC を
  その場で合成する）は歩けない。判定は 1 クエリで済むので、歩けるときだけ歩く。
  1 名前 1 クエリの直列処理になるため、件数と時間の両方で上限を掛け、
  どちらで打ち切ったかを必ず結果に出す。
- 子ゾーンへの委譲点では `\000.name` がリゾルバを子ゾーンに送ってしまい親の NSEC が返らない。
  最左ラベルの末尾に最小バイトを足した兄弟名で、サブツリーごと飛び越えている。
- Wikimedia の `exturlusage` は匿名リクエストの同時接続を IP 単位で絞っている。
  7 プロジェクトを並列に投げると後続が 429 になるため（実測: 並列 2 で 4/7 が失敗、
  直列なら 0 件）、直列に回して時間で上限を掛けている。
  照会が回りきらなかったプロジェクトは「参照なし」ではなく「未照会」として区別し、
  1 つでも未照会があれば「痕跡なし」とは判定しない。
  調べるのは 7 プロジェクトのみで、言語版は 300 以上あるため網羅ではない。
- dangling 判定はアンダースコア始まりの名前（`_dmarc`, `_acme-challenge`, `_25._tcp` など）を
  対象外にしている。TXT / TLSA / OPENPGPKEY といった A 以外のレコード型を使うため、
  そのまま判定すると正常な設定を軒並み誤検出する。

## 開発

```sh
npm install
npm run dev
```

外部 API に対してスキャナを直接動かす場合:

```sh
npx tsx scripts/probe.ts example.com
```

短時間に何度も回すと certspotter と Wikimedia のレート制限に当たり、
結果が「判定不能」に劣化する。連続で叩かないこと。

## デプロイ

`main` への push で GitHub Pages に配信される (`.github/workflows/deploy.yml`)。
リポジトリ名がパスに入るため、ビルド時に `MITORI_BASE` で base を差し替えている。
